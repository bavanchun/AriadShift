# Phase 1: Engine packs

## Goal

`ashift engines install <pack>` downloads a signed pack manifest, verifies its minisign signature against a key compiled into `ashift`, downloads and SHA-256-verifies each component for the current target, extracts it safely, and registers the pack so the host can launch its engine. This is the mechanism the docling pack (phase 4), the desktop pack manager (phase 8) and the cloud worker images (phase 9) build on.

Read first: ARCHITECTURE.md §7 and §7.1, `crates/ariad-host/src/engines/`, `crates/ariad-host/src/commands/{engines,doctor}.rs`, `crates/ariad-cli/src/main.rs`, `docs/cli.md`.

## Requirements

### Manifest and signature

- Manifest `ariad-pack/1`, TOML, with a JSON Schema `schemas/pack.v1.json` generated by `schemars` and drift-tested like the other schemas.
- Fields: `schema`, `name`, `version`, `description`, `license` (SPDX summary), `requires_ashift` (semver requirement), `notices` (relative paths of licence files inside the pack), and `[[targets]]` with `triple`, `entrypoint` (argv relative to the install root), `env` (allow-listed engine settings such as `HF_HUB_OFFLINE`), `options` (default request options, values may reference `{root}`), and `[[targets.components]]` with `name`, `url`, `sha256`, `size`, `unpack` (`tar.zst`, `tar.gz`, `zip`, `file`) and `dest` (relative directory).
- Detached signature `pack.toml.minisig` in minisign format, verified with `minisign-verify` (pure Rust). The trusted comment must name the pack and version; a mismatch is a verification failure (stops mixing a manifest with another version's signature).
- Public keys compiled in from `crates/ariad-host/data/pack-keys/*.pub` (a list, so keys can rotate). Tests use a throwaway key generated in the test; the production key is added in phase 5.

### Index, download, install

- An embedded index `crates/ariad-host/data/packs.toml` lists known packs: name, recommended version, manifest URL template (`https://github.com/bavanchun/AriadShift/releases/download/pack-<name>-v<version>/pack.toml`).
- `ashift engines install <name> [--version <v>] [--manifest <url-or-path>] [--from <dir>]`: `--from` installs from a local directory holding the manifest, signature and component files (offline, air-gapped).
- HTTPS client with rustls (pure-Rust TLS that builds for the musl release targets), connect and read timeouts, a bounded retry, proxy environment variables honoured. Stream each component to a staging file while hashing; abort on size or hash mismatch.
- Extraction with hard rules: no absolute paths, no `..`, no symlink or hard link that resolves outside the install root, no device files, file count and total size bounded by the manifest's declared sizes with a margin. Prefer pure-Rust decoders (`tar`, `ruzstd`, `flate2` with the Rust backend, the existing `zip`).
- Install into `<data>/packs/.staging/<random>`, then rename to `<data>/packs/<name>/<version>` and write a receipt (`receipt.toml`: manifest copy, install time, per-file SHA-256 list). A lock file prevents concurrent installs of the same pack.
- `<data>` is `ASHIFT_DATA_DIR` when set, otherwise the platform data directory for `com.ariadnev.ariadshift` (`directories` crate).
- `ashift engines remove <name> [--version <v>]`, `ashift engines verify <name>` (re-hashes files against the receipt), and `ashift engines` gains an installed-packs section. Every new command has `--json`.
- A hidden `ashift __pack manifest --name … --version … --target … <component files>…` writes an unsigned manifest with sizes and hashes; phases 4 and 5 use it to build packs.

### Engine resolution

- `ariad_host::packs::resolve(name) -> Option<InstalledPack>` returns the install root, version, entrypoint and resolved options for the current target. An environment override `ASHIFT_PACK_<NAME>=<dir>` points at an unpacked development pack.
- `doctor` reports the data directory, its writability, installed packs, their verification state and the compiled-in key ids.
- MCP `list_engines` includes installed packs. Installing stays CLI and desktop only.

## Acceptance criteria

- Tests with a local HTTP server cover: valid install; bad signature; wrong key; trusted-comment mismatch; component hash mismatch; size mismatch; archive with `..`, absolute path, escaping symlink, device file; interrupted download leaves no staging residue; reinstall is idempotent; remove; verify detects a modified file; unsupported target error; `requires_ashift` mismatch error.
- `--from` installs offline.
- Exit codes follow the table in ARCHITECTURE §4 (signature or hash failure is 1 with a typed message; a missing pack in the index is 3).
- New dependencies are permissively licensed, allowed by `deny.toml`, and build for every release target (`dist plan` unchanged in shape; the musl build still links).
- `docs/cli.md`, a new `docs/packs.md` (format, layout, signing and publishing procedure), ARCHITECTURE §7.1 and the Decision Log are updated.

## Risks

| Risk | Response |
|---|---|
| TLS stack needs a C toolchain on musl | Check the release workflow's musl build locally (`cargo build --target x86_64-unknown-linux-musl`) or in the PR run; pick the provider that links |
| Zip-slip or symlink tricks in a malicious archive | Fuzz-style table tests plus a resolved-path check after every entry |
| Huge components (about 1 GB) | Streamed hashing, no whole-file buffering, progress on stderr only when it is a TTY |

### Layout

- `crates/ariad-host/src/packs/`: `mod.rs` (public API, context, errors), `manifest.rs`, `signature.rs`, `index.rs`, `fetch.rs`, `extract.rs`, `install.rs` (install, remove, verify, receipts, locks), `author.rs` (`__pack manifest`).
- `crates/ariad-host/build.rs` embeds the build target triple and every `data/pack-keys/*.pub` file; `data/pack-keys/` starts empty (production key arrives with the first signed pack).
- `crates/ariad-host/data/packs.toml`: embedded index (`schema = "ariad-pack-index/1"`, one `[[packs]]` entry per known pack, `manifest` URL template with `{name}` and `{version}`).
- `schemas/pack.v1.json`: generated from `packs::Manifest`, drift-tested in `crates/ariad-host/tests/pack_schema.rs` with the same `ARIAD_BLESS_SCHEMAS=1` switch.

### Data directory

`ASHIFT_DATA_DIR`, else `ProjectDirs::from("com", "ariadnev", "ariadshift").data_local_dir()` (local, not roaming, AppData on Windows: packs are large).

```text
<data>/packs/
  .locks/<name>.lock        # File::try_lock; install and remove of one pack are exclusive
  .staging/<name>.<uuid>/   # extraction target, renamed into place, swept under the lock
  .cache/<name>.<sha256>    # fully downloaded and hash-verified components (resume); `.part` while downloading
  <name>/current            # active version
  <name>/<version>/         # install root: components, plus receipt.toml (reserved name)
```

### Manifest `ariad-pack/1`

Pack fields as specified. Component additions: `unpacked_size` and `entries` (required for archive modes; the extraction bound is the declared value plus 1 % plus 1 MiB or 16 entries), and `executable` (for `unpack = "file"`, which writes `<dest>/<name>`). A relative `url` resolves against the manifest location, so a release can hold the manifest and its components side by side. Remote URLs must be `https://`; `http://` is accepted only for loopback hosts (integrity comes from the signature and hashes, and the test server needs it). The manifest header (`schema`, `requires_ashift`) is checked before the strict parse so a newer manifest yields a version error instead of a parse error. `env` names come from an allow-list (Hugging Face offline switches, `TESSDATA_PREFIX`, thread counts, Python runtime switches); `{root}` is substituted in `env`, `options` and entrypoint arguments.

Trusted comment: whitespace-separated `key:value` tokens that must include `pack:<name>` and `version:<version>` (sign with `minisign -S -t "pack:docling version:0.2.0"`).

Targets: the pack triple describes the pack's own binaries, not `ashift`'s. Linux hosts accept `<arch>-unknown-linux-gnu` when a glibc loader exists, then `<arch>-unknown-linux-musl`, so the static musl `ashift` installs glibc packs.

### Public API (stable for consumers)

```rust
pub struct InstalledPack {
    pub name: String, pub version: String, pub target: String,
    pub root: PathBuf,                       // install root; grant read-only to the engine
    pub program: PathBuf,                    // entrypoint[0] joined to root
    pub args: Vec<OsString>,                 // entrypoint[1..], `{root}` substituted
    pub env: Vec<(OsString, OsString)>,      // allow-listed, `{root}` substituted
    pub options: serde_json::Map<String, Value>, // default request options
    pub source: PackSource,                  // Installed | Override
}
pub fn resolve(name: &str) -> Option<InstalledPack>;
pub fn try_resolve(name: &str) -> Result<Option<InstalledPack>, PackError>;
```

`ASHIFT_PACK_<NAME>` (upper case, `-` as `_`) points at an unpacked directory holding `pack.toml`; no signature, no receipt. `runner::run_with_env` and `runner::describe_with_env` pass a pack's environment through the cleared engine environment. `ashift engines` and MCP `list_engines` describe each resolved pack through its entrypoint; `EngineRow` gains an optional `pack` object (additive JSON change, array shape kept). The planner's cached availability is unchanged: conversions query it on every run, and routing to a pack engine belongs to the engine that ships in the pack.

### CLI

- `ashift engines install <name> [--version V] [--manifest URL|PATH | --from DIR] [--json]`, `remove <name> [--version V] [--json]` (all versions when omitted), `verify <name> [--version V] [--json]` (full re-hash against the receipt plus a signature re-check). Human output prints the install root; JSON output carries no absolute paths.
- `ashift __pack manifest --name N --version V --target T [--base FILE] [--entrypoint ARG]… [--url-prefix URL] [--dest COMPONENT=DIR]… [-o FILE] [NAME=]FILE…` writes or updates the target's components (size, SHA-256, unpack mode from the extension, unpacked size and entry count from a dry-run of the extractor). With `--base` the other targets are kept, which lets a release merge per-target builds.
- Exit codes: unknown pack, not installed and unsupported target 3; `requires_ashift` mismatch 5; signature, hash, size, unsafe archive, network and I/O failures 1; extraction beyond the declared bounds 4; interruption 130. Pack commands share `run_blocking` through a small error trait.
- `doctor`: non-required checks `data_dir` (writable), `pack_keys` (compiled-in key ids) and `pack_<name>` (receipt, signature and file presence and sizes; full hashing stays in `engines verify`).

### Deviations

- Per-component `unpacked_size`, `entries`, `executable`: needed for the declared-size bound and single-file engines.
- `--base`, `--entrypoint`, `--url-prefix`, `--dest` on `__pack manifest`: needed to produce a complete manifest and to merge targets built on different runners.
- `verify --version`: lets a non-active version be checked.

### Completion corrections

- Reinstall re-hashes existing files before returning `already_installed`, so changes that preserve file size are repaired.
- `zstd.rs` joins zstd data frames and skips metadata frames before the shared tar reader; scanning and extraction use the same stream.
- The lightweight pack health check re-verifies the receipt's manifest signature against the current keys; full file hashing remains in `engines verify` and reinstall.
- Cached component names include the pack name, matching the per-pack lock scope. Two pack installs with identical component bytes cannot delete each other's pending extraction inputs.
- Completed extraction must match the signed entry count and unpacked byte count exactly, in addition to the streaming upper limits.
- The TLS provider is selected explicitly. Certificate failures are permanent, carry the CA-bundle hint, and have a loopback HTTPS test for trusted and untrusted certificates.
- A clean EOF below the declared component size is `size_mismatch` for both online and offline installs; transport errors remain retryable.
