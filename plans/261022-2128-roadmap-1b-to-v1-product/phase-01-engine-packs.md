# Phase 1: Engine packs

## Goal

`ashift engines install <pack>` downloads a signed pack manifest, verifies its minisign signature against a key compiled into `ashift`, downloads and SHA-256-verifies each component for the current target, extracts it safely, and registers the pack so the host can launch its engine. This is the mechanism the docling pack (phase 4), the desktop pack manager (phase 8) and the cloud worker images (phase 9) build on.

Read first: ARCHITECTURE.md §7 and §7.1, `crates/ariad-host/src/engines/`, `crates/ariad-host/src/commands/{engines,doctor}.rs`, `crates/ariad-cli/src/main.rs`, `docs/cli.md`.

## Requirements

### Manifest and signature

- Manifest `ariad-pack/1`, TOML, with a JSON Schema `schemas/pack.v1.json` generated by `schemars` and drift-tested like the other schemas.
- Fields: `schema`, `name`, `version`, `description`, `license` (SPDX summary), `requires_ashift` (semver requirement), `notices` (relative paths of licence files inside the pack), and `[[targets]]` with `triple`, `entrypoint` (argv relative to the install root), `env` (allow-listed engine settings such as `HF_HUB_OFFLINE`), `options` (default request options, values may reference `{root}`), and `[[targets.components]]` with `name`, `url`, `sha256`, `size`, `unpack` (`tar.zst`, `tar.gz`, `zip`, `file`) and `dest` (relative directory).
- Detached signature `pack.toml.minisig` in minisign format, verified with `minisign-verify` (pure Rust). The trusted comment must name the pack and version; a mismatch is a verification failure (stops mixing a manifest with another version's signature).
- Public keys compiled in from `crates/ariad-host/data/pack-keys/*.pub` (a list, so keys can rotate). Tests use a throwaway key generated in the test; the production key is added in phase 5.

### Index, download, install

- An embedded index `crates/ariad-host/data/packs.toml` lists known packs: name, recommended version, manifest URL template (`https://github.com/bavanchun/AriadShift/releases/download/pack-<name>-v<version>/pack.toml`).
- `ashift engines install <name> [--version <v>] [--manifest <url-or-path>] [--from <dir>]`: `--from` installs from a local directory holding the manifest, signature and component files (offline, air-gapped).
- HTTPS client with rustls (pure-Rust TLS that builds for the musl release targets), connect and read timeouts, a bounded retry, proxy environment variables honoured. Stream each component to a staging file while hashing; abort on size or hash mismatch.
- Extraction with hard rules: no absolute paths, no `..`, no symlink or hard link that resolves outside the install root, no device files, file count and total size bounded by the manifest's declared sizes with a margin. Prefer pure-Rust decoders (`tar`, `ruzstd`, `flate2` with the Rust backend, the existing `zip`).
- Install into `<data>/packs/.staging/<random>`, then rename to `<data>/packs/<name>/<version>` and write a receipt (`receipt.toml`: manifest copy, install time, per-file SHA-256 list). A lock file prevents concurrent installs of the same pack.
- `<data>` is `ASHIFT_DATA_DIR` when set, otherwise the platform data directory for `com.ariadnev.ariadshift` (`directories` crate).
- `ashift engines remove <name> [--version <v>]`, `ashift engines verify <name>` (re-hashes files against the receipt), and `ashift engines` gains an installed-packs section. Every new command has `--json`.
- A hidden `ashift __pack manifest --name … --version … --target … <component files>…` writes an unsigned manifest with sizes and hashes; phases 4 and 5 use it to build packs.

### Engine resolution

- `ariad_host::packs::resolve(name) -> Option<InstalledPack>` returns the install root, version, entrypoint and resolved options for the current target. An environment override `ASHIFT_PACK_<NAME>=<dir>` points at an unpacked development pack.
- `doctor` reports the data directory, its writability, installed packs, their verification state and the compiled-in key ids.
- MCP `list_engines` includes installed packs. Installing stays CLI and desktop only.

## Acceptance criteria

- Tests with a local HTTP server cover: valid install; bad signature; wrong key; trusted-comment mismatch; component hash mismatch; size mismatch; archive with `..`, absolute path, escaping symlink, device file; interrupted download leaves no staging residue; reinstall is idempotent; remove; verify detects a modified file; unsupported target error; `requires_ashift` mismatch error.
- `--from` installs offline.
- Exit codes follow the table in ARCHITECTURE §4 (signature or hash failure is 1 with a typed message; a missing pack in the index is 3).
- New dependencies are permissively licensed, allowed by `deny.toml`, and build for every release target (`dist plan` unchanged in shape; the musl build still links).
- `docs/cli.md`, a new `docs/packs.md` (format, layout, signing and publishing procedure), ARCHITECTURE §7.1 and the Decision Log are updated.

## Risks

| Risk | Response |
|---|---|
| TLS stack needs a C toolchain on musl | Check the release workflow's musl build locally (`cargo build --target x86_64-unknown-linux-musl`) or in the PR run; pick the provider that links |
| Zip-slip or symlink tricks in a malicious archive | Fuzz-style table tests plus a resolved-path check after every entry |
| Huge components (about 1 GB) | Streamed hashing, no whole-file buffering, progress on stderr only when it is a TTY |
