# Review: feat/v1-hardening, services, infra, CI and scripts

Reviewed 2026-10-27 (Asia/Saigon), read-only, against `origin/dev` at `e6bd29b` and `origin/feat/v1-hardening` at `dcb34bc`. Nothing was built, run, fetched or checked out.

## 1. Verdict

**Needs fixes.** One high finding blocks the merge. The fix for anonymous OAuth client registration lives only on `feat/v1-hardening--oauth-rev` and never reached this branch, although this branch's committed report says it is fixed. Three medium findings and a CI gap should also be closed before the branch merges into `dev`.

### What the branch actually changes in scope

The merge base is `68ac304` (#48). Since then `dev` has squash-merged the cloud foundation (#53, `8782c49`) and the Docling Intel exclusion (#51). The three-dot diff a PR would show is therefore about 25,900 lines, but most in-scope infra is already on `dev`. Compared tree to tree with `origin/dev`, the changes this branch adds are:

- `services/auth`: the OAuth authorization server for remote MCP (`@better-auth/oauth-provider` 1.7.12), a serialized token handler (`oauth-lock.ts`), sign-in and consent pages, and tests.
- `infra/compose/docker-compose.yml`: passes `ARIAD_PUBLIC_URL` to `auth` (3 lines).
- `infra/test/e2e/mcp-oauth.sh` and the `just mcp-oauth-e2e` recipe.
- `.github/workflows/ci.yml`: 18 PR fuzz targets instead of 9, timeout raised from 35 to 45 minutes.
- `.github/workflows/fuzz-nightly.yml`: one ASan target per matrix job, 9 targets.

The workers, seccomp profile, gVisor overlay, Postgres bootstrap, SeaweedFS scripts, `images.yml` and `scripts/ci-scope.sh` are byte-identical to `dev`. They are covered under "pre-existing" at the end.

## 3. Contract and architecture

- **No boundary violation found.** No conversion logic moves into a surface. The OAuth server stays in `services/auth`, the separate Node service the Decision Log already approves, and the new "Remote MCP authorization" row records the dependency, as AGENTS.md requires.
- **The auth service's environment contract changed.** `ARIAD_PUBLIC_URL` is now required by `auth`, and both origins must be HTTPS outside loopback. `.env.example`, `docs/self-hosting.md` and the README's configuration table document it, but finding 3 makes it a breaking change for existing deployments.
- **The two services do not handle a path in `ARIAD_PUBLIC_URL` the same way.** `ariad-server` accepts a URL with a path and builds the resource as `<origin>/mcp`, dropping the path (`mcp/mod.rs` `resource_url`). The auth service refuses any path (`config.ts:70`), so an operator with a path-prefixed API URL gets an auth service that will not start. See Q2.
- **REST and MCP audiences are kept apart in source.** The API JWT carries `aud` = the auth origin. MCP tokens carry `aud` = `<ARIAD_PUBLIC_URL>/mcp`, with the UserInfo URL added for `openid`. Neither equals the other's expected value, and the e2e script checks that the API JWT is refused at `/mcp`. `client_credentials` is excluded, which prevents a client id from becoming a `sub`.
- **ARCHITECTURE.md has small drift.** Line 614 lists the Better Auth-owned tables without the OAuth provider's (`oauthClient`, `oauthAccessToken`, `oauthRefreshToken`, `oauthConsent`, `oauthClientResource`, ...). The stack row at line 69 does not list the OAuth provider plugin.
- **Licensing.** `scripts/check-js-licenses.mjs` covers the workspace's production dependencies, so the new provider and its transitive packages are gated in `just static`. That gate was not run here.

## 4. Test gaps that matter

1. **The PostgreSQL serialization suite never runs in CI.** `services/auth/test/oauth-postgres.test.ts:19-21` is `describe.skipIf(!process.env.ARIAD_TEST_DATABASE_URL)`. Vitest runs in the web job (`ci.yml`, `just web-ci`), which has no database. The server job has the database (`ci.yml:297`) but runs only `cargo nextest`. This suite is the only regression for the refresh-family race fixed after the earlier high finding, and for the lock deadlines. Run `pnpm --filter @ariadshift/auth test` in the server job with `ARIAD_TEST_DATABASE_URL` and a PostgreSQL 18 `pg_dump`, or make the skip fail when `CI=true`.
2. **`just mcp-oauth-e2e` is not wired into any workflow.** The only end-to-end check of discovery, registration, consent, MCP conversion and refresh through compose is manual.
3. **There are no tests for the open findings.** No test covers registration volume or abuse (finding 1), token-endpoint starvation (finding 2), or non-loopback HTTP startup, nor would one tell an operator why the stack did not start (finding 3).
4. **Two-factor during OAuth is not tested end to end.** No case checks that a password-only sign-in with 2FA enabled yields no code (M7 of the earlier review).
5. **Nightly ASan covers 9 of the 18 fuzz targets.** `pack_manifest`, `engine_protocol`, `uri_parsers`, `capabilities_json`, `asset_resolve`, `ir_json_versioned`, `front_matter`, `limits_validate` and `typst_writer` run only the 60-second PR pass. These parsers are safe Rust, so the value is low, but `pack_manifest` and `engine_protocol` read untrusted input. The CI change itself is sound: `matrix.target` reaches the shell through `env`, so there is no template injection, and the per-target cache and artifact names do not collide.

### Compose with no external accounts

Yes, on the default loopback settings. GitHub, Google and Turnstile are off when their variables are empty, PostgreSQL and SeaweedFS are local, every image builds from the repository, and `auth` gets the `ARIAD_PUBLIC_URL` default `http://localhost:8080`. The e2e script generates its secrets from `.env.example`. Builds still need network access to pull base images and pnpm, but no account. Finding 3 is the exception: any non-loopback HTTP origin now stops the stack.

### Pre-existing on dev (landed in #53, not introduced here)

- **Medium: SeaweedFS's internal APIs are reachable without authentication from every container on the `edge` network.** `seaweedfs` joins `edge` (`docker-compose.yml:108`) and binds everything to `0.0.0.0` (`seaweedfs/start.sh`). No `security.toml` JWT is configured, so `web` (edge only), `api` and `auth` can reach master `:9333`, volume `:8080` and filer `:8888` directly. That bypasses the single bucket-scoped S3 identity: a compromised web container could read or write every user's documents through the filer. Put the published S3 port behind a dedicated network or proxy, or enable SeaweedFS JWT signing for filer and volume.
- **Low: compose can start with publicly known secrets.** `.env.example` placeholders such as `BETTER_AUTH_SECRET=replace-with-openssl-rand-hex-32-better-auth` (44 characters) pass compose's `:?` checks and the auth service's 32-character minimum, so a stack where they were never replaced starts with known secrets. `BIND_ADDRESS=127.0.0.1` limits the exposure. Reject values that start with `replace-with` at startup.
- **Accepted and documented: the Office and Docling worker sandbox.** Those workers use a seccomp profile that adds `unshare(CLONE_NEWUSER|CLONE_NEWNS)` and an unconditional `mount`, with AppArmor lifted, and the gVisor overlay drops the engine sandbox to best-effort. Both trade-offs are recorded in comments and `docs/server.md`. Nothing new.

## 5. Unresolved questions

1. Should `e7101d8` be merged as is, or should the coordinator also add the purge and an operator switch to disable anonymous registration before v1?
2. Is a path-prefixed `ARIAD_PUBLIC_URL` (an API behind `/api` on a shared host) a supported deployment? If yes, both services must agree on the resource. Today `ariad-server` drops the path and `auth` refuses to start.
3. Is plain-HTTP LAN self-hosting a supported v1 scenario? The answer decides whether finding 3 needs a code change or only an upgrade note.
4. Does Better Auth 1.7.12 route trailing-slash paths and accept duplicate signed-query parameters? This decides whether findings 5 and 7 are display-only or functional. It needs a read of the pinned library source.
