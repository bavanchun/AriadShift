Date: 2026-10-27 (Asia/Saigon). Reviewer: Mac console, read-only.

Subject: [console-review-261027-1935-distribution.md](console-review-261027-1935-distribution.md). This pass checks findings 1, 2 and 3 (High) and findings 5 and 6 (Medium, with a security angle). It also looks for High issues in the same scope that the first review missed.

Refs used: `origin/feat/v1-distribution` = `2e860da`, `origin/dev` = `e6bd29b`, merge base `e0f68a8`. These are the same refs as the first review. ## 1. Verdict

**Needs fixes.** Two of the five checked findings hold as written (2 and 5). Findings 1, 3 and 6 are directionally right, but each one has a wrong premise or an overstated part. The biggest correction is to finding 1. `dev` (#51) has already redefined the Docling **0.2.0** pack as `>=0.2.0, <2.0.0`, and `dev`'s docs say that pack is not yet published. So the fix is to merge `dev` and publish 0.2.0 from the merged builder; a new pack version is not needed. I found no new High issue. I found one new Medium integration break: the SDK lock fails once `dev` is merged.

## 3. Contract or architecture violations

- **Docs against `dev`'s policy.** After integration, the branch's `docs/release-notes.md:36` and `docs/server.md:38` would contradict `dev`'s `docs/packs.md#compatibility`. They would tell users that a 1.0.0 host refuses the 0.2.0 pack, when the documented policy says it accepts it. Users would be steered toward a reinstall that is neither needed nor possible.
- **Unrecorded trust change.** The pack signing key moving from a manual release step into automated CI is not in the Decision Log. Row 947 records only "the project key".

## 4. Test gaps that matter

- No test ties `REQUIRES_ASHIFT`, `packs.toml` and `CARGO_PKG_VERSION` together. `dev`'s `docling_pack.rs` assertion covers the builder range, but only if that hunk survives the merge.
- No test covers the resolve-time refusal for an installed pack whose range excludes the running host. The existing `requires_ashift_mismatch_is_a_version_error` test (`crates/ariad-host/tests/packs.rs:813`) covers install only (I did not read its body).
- Nothing checks the desktop installers that are not updater artifacts (`.dmg`, `.msi`, `.deb`, `.rpm`) between the build and `sign-release`.

## 5. Unresolved questions

1. Has any `pack-docling-v0.2.0` asset been published, and if so, does its `pack.toml` say `<0.3.0` or `<2.0.0`? This decides whether finding 1 needs only the merge or also a re-publish.
2. Does the `release` environment have required reviewers and a deployment-tag rule, and are `v*` tags protected by a ruleset? This decides how much finding 6 adds over the existing state.
3. Is `PACK_MINISIGN_KEY` actually stored in the `release` environment today, as `docs/packs.md:171` instructs, or does it live only offline? If only offline, finding 6's new exposure is larger than stated here.
