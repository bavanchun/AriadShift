# Review: feat/v1-hardening, desktop OS integration, macOS Seatbelt, doctor

Scope: `git diff origin/dev...origin/feat/v1-hardening` (merge base `68ac304`) limited to
`apps/desktop`, `crates/ariad-host` and `crates/ariad-cli`. Surrounding code read on the merge
base where the branch leaves it unchanged (runner, doctor, engine sandbox paths, CLI tests,
vendored deep-link plugin, single-instance 2.5.4 from the cargo registry). Nothing was built or
run; every finding below comes from reading code.

## 1. Verdict

Needs fixes. The macOS `verify` CI job will fail on three existing tests that still expect macOS
to skip the sandbox. On macOS every Finder or Quick Action open also shows a false "Invalid
desktop link" error. Seatbelt is now on by default for every macOS engine, but nobody has run it
against LibreOffice or Docling, and the sandbox has a concrete way to break LibreOffice.

Verified non-issues:
- Paths are passed as `-D` parameters and never interpolated into SBPL, and symlink escapes are covered by the tests.
- Only parsed integers enter the bash `ulimit` script.
- `required` refuses to run without Seatbelt.
- `opened_files` widens nothing, because existing commands already accept arbitrary paths, and its `allow-opened-files` permission is generated from `command_table::NAMES`.
- Cold-launch files survive until the window's first drain, because Tauri creates config windows before `setup`.
- The `.app` ancestor grant only widens access to the bundle that holds the engine program, which for the desktop app is its own bundle.

## 3. Contract and architecture violations

- **ARCHITECTURE.md §11.3 (line 714) is now wrong.** It says macOS uses process groups only, the launcher is not used, `required` is unavailable and "Seatbelt remains later hardening work". The branch adds a new isolation layer (a `sandbox-exec` plus `/bin/bash` exec chain, best-effort by default on macOS, `required` supported) and no Decision Log entry. AGENTS.md requires both updates in the same change. The phase 6 final review raised this too; it is still open.
- **ARCHITECTURE.md line 557** plans Windows 11 Explorer integration through `IExplorerCommand` and sparse packaging. The branch ships classic `SystemFileAssociations` verbs, which Windows 11 shows only under "Show more options". That is a deviation with no Decision Log row.
- Engine logic stays in `ariad-host`, and no third-party code is linked. The platform-specific doctor presentation in the CLI is not conversion logic, but it duplicates host knowledge and leaves the desktop out (see findings).

## 4. Test gaps that matter

- No automated or recorded run of LibreOffice or Docling under Seatbelt. The macOS CI runner has no LibreOffice, so `builtin_engine_contracts` skips Office.
- No evidence that `sandbox_macos.rs` has ever run. The worker and integration reports defer runtime validation to the coordinator.
- No desktop test for the macOS `Opened` and deep-link overlap (file URLs reaching `parse_link`).
- No assertion on the macOS `doctor --json` fields `seatbelt_available`, `seatbelt_usable` and `seatbelt_enforced`, and no test of the host doctor wording on macOS.
- Nothing runs the generator drift test (see findings).
- No test of a Windows multi-file Explorer launch through single-instance (manual installer check only).

## 5. Unresolved questions

- Has the `macos-26` `verify` job run on the branch head? `gh run list` needed approval, so the CI state is unknown.
- Has anyone run a real LibreOffice conversion through the Seatbelt launcher on a Mac? If it fails, should Office be exempted with a reported gap, or should the profile grant a private IPC directory?
- Is HKCU-only intended for the per-machine MSI, or should the MSI write HKLM or become per-user?
- Should the desktop expose a sandbox-mode setting now that best-effort enforces Seatbelt on macOS?
- Windows 11: are classic verbs under "Show more options" the accepted v1 scope, replacing the `IExplorerCommand` plan in ARCHITECTURE.md?
