# Review: fuzz targets, seeds and fuzz CI on `feat/v1-hardening`

Scope: `git diff origin/dev...origin/feat/v1-hardening` (merge base `68ac304`, branch head `dcb34bc`) for `fuzz/`, `.github/workflows/ci.yml` (Fuzz job), `.github/workflows/fuzz-nightly.yml`, `justfile` (`fuzz`), `scripts/ci-scope.sh`, `docs/ci.md`, and the fuzz rows in `ARCHITECTURE.md`. `ariad-core` and `ariad-host` (apart from `sandbox*`) are identical at the merge base and the branch head, so the library code the harnesses call was read from the working tree. Nothing was built, fuzzed or executed. I could not query GitHub Actions for this branch's CI runs because `gh run list` needed approval.

## 1. Verdict

**Needs fixes.** Reading the code, the new `ir_json_versioned` target should panic on its own committed seeds. That would fail the required CI **Fuzz** job on every heavy run. Two other harnesses have a false-positive oracle or skip the trust boundary they claim to cover.

## 3. Contract and architecture checks

- **Date-pinned nightly exception: complies.** Only `fuzz-nightly.yml` uses `nightly-2026-10-05`, at lines 56 and 86. No other workflow, recipe or script references a nightly toolchain. The PR Fuzz job stays on stable with `-s none`. The `pull_request` trigger for workflow edits predates this branch.
- **Fixtures and licensing: no violation found; one open question.** The binary seeds are byte-identical copies of fixtures already recorded in `fixtures/manifest.toml`: `fixtures/epub/en-epub-minimal.epub` and `fixtures/office/vi-garden-notes.{doc,odt}`, `vi-route-sheet.{xls,xlsx}`. The new synthetic seeds have no manifest entries. These are the stampable EPUB and XLSX, the pack archives, and the XML, OPF, TOML, JSON and JSONL seeds. That matches existing practice, since no fuzz seed on `dev` is recorded either. I saw no CC-BY-SA, GPL or private content. The pack seeds contain only the production *public* key `D87B0E33F55EA02B` and zero-filled signatures, with no secret key.
- **Dependencies: no change.** `fuzz/Cargo.toml` adds only `[[bin]]` entries, and `fuzz/Cargo.lock` is unchanged. Every API the new targets call is `pub` in `ariad-host` or `ariad-core` and not behind a feature flag, and every `match` on an error enum covers all variants.
- **Boundaries: no violation.** The harnesses call library code only and add no conversion logic to any surface.
- **Docs rule: one miss.** `ARCHITECTURE.md` §14 was not updated for the nightly target change (finding 9).

## 4. Test gaps that matter

- `ir_json_versioned` only has legacy seeds. There is no `ariad-ir/1` seed and no future-version seed, so the version gate is barely exercised even after fixing finding 1.
- The compromised-engine boundary (`parse_event`, artifact confinement, the 1 MiB line limit) and the install-time pack extraction (`Writer` sink) are not fuzzed (findings 3 and 4).
- In `archive_preflight`, `assert_safe_names` (lines 44-64) restates `validate_entry_name` (`archive.rs:509-528`), so it catches regressions, not missing rules. Examples of rules it would not catch: NUL in names, Windows device names, trailing dots and spaces.
- `docx_meta` never checks the stamped *content*. `stamp_properties` drops only `Text` and `CData` inside a date element (`package_meta.rs:142`). If quick-xml 0.42 emits entity references such as `&amp;` as separate `GeneralRef` events (unverified), `<dcterms:created>x&amp;y</dcterms:created>` would be stamped as `&amp;<timestamp>`, and the harness would accept that. Asserting that each date element holds exactly the timestamp would catch it.
- The signed path in `pack_manifest` is unreachable (finding 5).
- No fuzz run, build or duration measurement backs these targets yet. `plans/reports/code-review-261025-phase6-final.md:167` says no fuzz run was done, and the 45-minute CI budget is still unmeasured.

## 5. Unresolved questions

1. Has the CI Fuzz job run on `dcb34bc` or any commit that contains `ir_json_versioned`? A green run would contradict finding 1, so the job log is worth checking.
2. Do fuzz seeds count as "fixtures" under AGENTS.md's `fixtures/manifest.toml` rule? If yes, both the existing and the new synthetic seeds need entries.
3. Does zip 9.0.5's `raw_copy_file`/`start_file` re-encode CP437 entry names as UTF-8? This decides whether finding 6 is a real false positive.
4. Were `pack_manifest`, `engine_protocol`, `capabilities_json`, `asset_resolve`, `uri_parsers` and `ir_json_versioned` left out of the ASan matrix on purpose, as pure safe-Rust parse paths? `asset_resolve` reaches `cap-std` and `pack_manifest` reaches `minisign-verify`.
