## 3. Contract and architecture violations (re-checked)

- ARCHITECTURE.md:27 (Principle 6, resource limits): confirmed by H3–H8, M4, M5 and M8–M13.
- ARCHITECTURE.md:344 says the Markdown reader "iteratively enforces … nesting". That holds for blocks only (H2). ARCHITECTURE.md:346 defines `max_nesting_depth` as block plus inline for HTML, so the two readers disagree.
- ARCHITECTURE.md:346: the stated ~230 B/byte bound for reconstruction does not hold for attribute-heavy input (H3).
- ARCHITECTURE.md:405, "emits only what is provably safe": violated by M2.

## 4. Test gaps that matter (re-checked)

- The `strip_html_tags` tests at `tests/writer_roundtrip.rs:1910-1933` are ASCII only (H1).
- The fuzz targets on origin/dev are `docling_to_ir`, `front_matter`, `html_reader`, `ir_json`, `limits_validate`, `markdown_reader`, `pandoc_ast_to_ir`, `pdf_reader` and `typst_writer`. None of them calls the Markdown or HTML writer, so a writer fuzz target fed by `read_ir_json` would hit H1.
- There is no inline-nesting test. Use the corrected `*a(`/`a*)` input, not `*(`.
- `rejects_hostile_nesting_before_calling_the_parser` (`reader/markdown.rs:1106-1122`) codifies M7.

## 5. Unresolved questions

1. Stack sizes for the desktop app (tokio workers default to 2 MiB), the MCP server, the web worker and the cloud `__convert` helper. These set the H2 crash threshold.
2. The Markdown prescan does not count GFM `~~` at all. Whether comrak nests `~~a ~~b~~ a~~` deeply was not checked; if it does, that is a second H2 vector.
3. Whether Pandoc's EPUB and DOCX readers emit `RawBlock "html"` for ordinary documents, which would widen H1 reach beyond Markdown and IR JSON input.
