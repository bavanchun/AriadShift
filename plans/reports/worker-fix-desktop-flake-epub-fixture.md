## Issue #120: Windows Desktop Cancel-Test Flake (`queued_jobs_cancel_without_creating_output`)

### Cause and Evidence
- In `apps/desktop/src-tauri/src/backend.rs` (`queued_jobs_cancel_without_creating_output`, lines 703–728), the test configured `concurrency: 1`, queued 100 Markdown-to-HTML jobs, cancelled only the last job (`jobs[99]`), and then called `wait(&app.backend, 100)`, which enforces a 20-second wall-clock timeout (`start.elapsed() < Duration::from_secs(20)` at line 584).
- Because only 1 of the 100 jobs was cancelled, the single worker thread had to execute 99 real conversions sequentially before `wait` returned. On slow `windows-2025` CI runners, 99 sequential conversions exceeded 20 seconds (22.6 s in CI run `41227075073`), causing `queue did not finish` panics.
- Meanwhile, cancelling a queued job in `Backend::cancel` (lines 217–231) is synchronous under `self.model.lock().unwrap()`: when `job.view.status == JobStatus::Queued`, it immediately marks `job.view.status = JobStatus::Cancelled` and `job.view.stage = "Cancelled".into()`.

### Fix
- Updated `queued_jobs_cancel_without_creating_output` in `apps/desktop/src-tauri/src/backend.rs` to cancel every queued job after the first in reverse order (`for job in jobs.iter().skip(1).rev()`), so `last` (`jobs[99]`) is cancelled first while guaranteed to be in `JobStatus::Queued`.
- Added a direct snapshot assertion (`assert_eq!(snap.jobs.last().unwrap().status, JobStatus::Cancelled)`) immediately after cancellation, then waited for the queue to drain (`wait(&app.backend, jobs.len())`, which now waits for at most `jobs[0]` instead of 99 conversions) and asserted both `done.last().unwrap().status == JobStatus::Cancelled` and `!Path::new(&last.output).exists()`.
- The 20-second timeout in `wait` was not raised. Execution time of `queued_jobs_cancel_without_creating_output` dropped from ~0.13s to ~0.05s locally on Linux (and avoids 98 redundant conversions on Windows).

## Issue #126 (Partial): EPUB Fixture Two-Run Convergence (`epub.py`)

### Cause and Evidence
- In `fixtures/gen/src/ariad_fixture_gen/__main__.py` (lines 32–37), all selected fixture generators run in memory (`outputs = {path: content for generator in selected.values() ...}`) before any generated bytes are written to disk.
- However, `fixtures/gen/src/ariad_fixture_gen/epub.py` (`_get_specs`, lines 277–282) checked `if route_png_path.is_file(): route_png = route_png_path.read_bytes()` against `fixtures/md/assets/vietnamese-route.png` on disk, falling back to `_route_image()` only if the file did not exist.
- Whenever `fixtures/md/assets/vietnamese-route.png` on disk differed from freshly generated `_route_image()` bytes (such as on macOS or when seeded with stale bytes), the first run of `ariad_fixture_gen` embedded the old disk bytes into `fixtures/epub/vi-epub-table-image.epub` and `fixtures/epub/vi-epub-table-image.truth.json` while `markdown.generate` overwrote `vietnamese-route.png` afterwards. Only on a second run did `epub.py` pick up the new PNG bytes.
- Verified with a failing test before the fix: running `(markdown.generate, epub.generate, truth.generate)` twice into a temporary root seeded with a stale `fixtures/md/assets/vietnamese-route.png` failed on `fixtures/epub/vi-epub-table-image.epub` (`AssertionError: ... EPUB output fixtures/epub/vi-epub-table-image.epub did not converge on the first run`).

### Fix
- Updated `fixtures/gen/src/ariad_fixture_gen/epub.py` to import `_route_image` from `ariad_fixture_gen.markdown` and always call `route_png = _route_image()` in `_get_specs(root)`.
- Added `fixtures/gen/tests/test_epub_idempotence.py` (`TestEpubIdempotence.test_two_runs_into_temporary_root_produce_identical_epub_bytes`), which copies the source text files into a temporary root, seeds a stale `fixtures/md/assets/vietnamese-route.png`, runs two full generation/write passes, and asserts that every `fixtures/epub/*` output is byte-identical between pass 1 and pass 2 and that `EPUB/images/route.png` inside `vi-epub-table-image.epub` matches the freshly generated `fixtures/md/assets/vietnamese-route.png` on the first run.

### Generator Regeneration Check on Linux
- Ran `just fixtures` (`uv run --package ariad-fixture-gen python -m ariad_fixture_gen`) across all 135 generated files on Linux.
- Neither `fixtures/epub/vi-epub-table-image.epub`, `fixtures/epub/vi-epub-table-image.truth.json`, `fixtures/manifest.toml`, nor any other generated fixture file changed on Linux (`git status` remained completely clean for all committed fixtures), because the committed `vietnamese-route.png` and EPUB fixtures were already generated with the Linux Pillow/zlib build.
- Unrelated generator rewrites on this Linux host: **none** (0 files modified by `just fixtures`).

### Test Names
