# Review: `crates/ariad-core` on origin/dev (readers, writers, IR, Typst writer)

Date: 2026-10-27 (Asia/Saigon). Reviewed ref: `origin/dev` at `e6bd29b`. The local `dev` worktree has no diff against `origin/dev` under `crates/ariad-core`, so every line number below is an origin/dev line number. Read-only review; nothing was built, run or fuzzed, so time and memory figures are estimates from the code.

## 1. Verdict

Needs fixes. There is a reachable panic on ordinary Vietnamese raw HTML in every native writer path. There is also an unbounded inline-nesting path in the Markdown reader that can overflow the stack. Several reader and writer paths are super-linear in time or memory and break the "Secure by default" resource-limit principle.

## 2. Findings

Severity reflects reachability from untrusted input on shipped surfaces (CLI, desktop, MCP, browser WASM, cloud worker). "Verified" means the defect was confirmed by reading the cited code. Where only the consequence was not executed, the row says so.

## 3. Contract and architecture violations

- **Principle 6, "Secure by default: resource limits" (ARCHITECTURE.md line 27).** Writers have no output budget (H8, M4, M5). Several reader paths are super-linear in time or memory (H3–H7, M8–M10, M13). The PDF module doc at `reader/pdf/mod.rs:8-15` claims a small file "cannot expand into unbounded work or output", which overstates the guarantee.
- **ARCHITECTURE.md line 344.** The Markdown reader "iteratively enforces … nesting", but inline nesting is not enforced (H2). `max_nesting_depth` therefore means block+inline in the HTML reader and block-only in the Markdown reader.
- **ARCHITECTURE.md line 346.** HTML reader memory is "bounded by its node budget", but attribute cloning breaks that bound (H3).
- **ARCHITECTURE.md line 348.** The shared link policy is not applied by the Markdown reader at read time (L2).
- **ARCHITECTURE.md line 405.** The Markdown writer "emits only what is provably safe", but footnote ids can carry raw HTML (M2).
- **IR contract (ARCHITECTURE.md lines 313 and 340).** `read_ir_json` does not enforce IR structural depth or `max_asset_bytes`, nor that `AssetRef::Asset.id` is the lowercase SHA-256 of the bytes (M4). The v1 schema allows a heading `level` of 0..255 (`schemas/ir.v1.json:146-151`), while every reader emits 1..=6. Whether writers must accept 0 or values above 6 is not stated.
- No crate, boundary, licence or unsafe-code violation was found in scope.

## 4. Test gaps that matter

- No unit test of `strip_html_tags` with multibyte text (H1). The existing tests (`tests/writer_roundtrip.rs:1912-1933`) are ASCII only.
- No fuzz target exercises the Markdown or HTML writers on arbitrary IR. `fuzz/fuzz_targets/` has only `typst_writer`, which caps nesting at 12 and input at 16 KB. A `markdown_writer`/`html_writer` target fed from `ir_io::read` would have found H1 immediately.
- No `*(`-style inline-nesting test (H2). `reader/markdown.rs:1112` asserts that a 70-`*` thematic break is rejected, which codifies M7.
- No adversarial performance or memory tests for: escaped `[^` runs and backtick-split `[^` lines (H5, H6), many `katex-html` siblings (H4), attribute-heavy formatting reconstruction (H3; the existing reconstruction test uses no attributes), nested `<code>` (M13), long hyphen-joined PDF blocks (H7), fonts sharing large `/Differences`, `/W` or CMap objects (M8, M9), huge operand arrays (M10), leading-space runs (M1), repeated asset references (H8), and wide or empty tables (M5).
- The existing fuzz targets catch super-linear paths only if they run with per-input `-timeout` and `-rss_limit_mb`. The CI fuzz configuration was not checked.
- No tests for text preservation around `[^]` or escaped footnote labels (M3), Markdown table captions or multiple header rows (M6), footnote ids containing `<` (M2), block content inside `<a>`, `<b>` or `<hN>` (M11), or a figure with extra content (M12).
- The PDF page-bounds invariant is checked only on real fixtures, never on synthetic off-page glyphs (L9).

## 5. Unresolved questions

1. What stack sizes do the reader and writer threads get in the desktop app, the MCP server, the web worker and the cloud `__convert` helper? That decides the input size at which H2 and deep IR from M4 crash.
2. Do local native surfaces run the isolated PDF engine with `timeout_s` and `max_memory_mb` unset? That decides whether H7 and M8–M10 hang or are killed.
3. Does layout cap the number of lines per PDF block? That decides the worst case of H7.
4. Does lopdf 0.46 decode all object streams eagerly when `strict: true` (L8)?
5. Should `ariad-ir/1` require Σcolspan ≤ `columns.len()`, unique `Footnote` ids, resolvable `FootnoteRef`s, a heading `level` of 1..=6, and asset id = SHA-256(bytes)? Today neither the schema nor `read_ir_json` enforces them.
6. Is `max_nesting_depth` meant to include Markdown inline nesting, as it does for HTML?
7. Is it intended that the Markdown and HTML writers append `furniture` to the body (`writer/markdown.rs:49`, `writer/html.rs:145`) while Typst drops it?
8. Can the cloud API accept IR JSON input directly? That decides how exposed M1, M4 and M5 are on the server.
