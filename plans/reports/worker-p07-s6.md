# OCR pipeline and evaluation

Status: in progress. Do not treat this report as gate evidence until the real-pack tests and measurements below have run.

The host composite dispatch, per-page PDFium render and Tesseract OCR, text-layer and sidecar generation, existing-text modes, optional deskew and orientation, conservative clean replacement, atomic output staging, and one shared deadline are implemented. Seven focused real-pack pipeline cases passed through the public registry, including Vietnamese text extraction, original image bytes, existing-text modes, blank-page orientation and cleaning an image-only page. Broader gate status is recorded in [the integration report](worker-p07-integrator.md).

The 50-page job passed on Linux with the source-built Tesseract pack and the updated development PDFium pack. `uv run --package ariad-bench --frozen python -m ariad_bench.ocr_stress --ashift <ashift> --fixture fixtures/scan/vi-garden-300dpi.pdf --output /tmp/ariad-p07-stress.json` duplicated the licensed one-page fixture with qpdf and ran the default 300 dpi `pdf.ocr` under a 2 GiB systemd scope and 600-second timeout. OCR took 469,839.63 ms (7 minutes 49.84 seconds), exited 0, and the process-tree sampler reported a 252,956,672-byte peak (241.24 MiB). The sampler sums process high-water RSS values, so it is a conservative sampled figure, not a cgroup peak. The fixture SHA-256 is `5201bd7748c43f8f15b73be83336ee5a8998e95997cb048ab150142b2c2fe3be`.

The CER/WER comparison below uses an actual Docling conversion through a development runtime with cached models and system Tesseract 5.5.3. The signed Docling 0.2.0 pack release is unavailable, and the development pack build did not complete.

`cargo check -p ariad-host -p ariad-cli` passed using the shared build lock. macOS Preview, Windows and musl remain unverified. No running server was started by this work.

The first real-pack `ocr_pipeline` run compiled successfully: the image-to-hOCR case passed with the source-built Tesseract pack. The three PDF cases failed because the shared development PDFium pack predates `scan.render` and correctly returned unsupported tool. That failure is not counted as a pass; a separate updated pack was built for the reruns below.

The current engine was then built and packaged separately at `/tmp/ariad-p07-pdfium`, using the hash-verified pinned PDFium archive; its 24 notices passed `engines/pdfium/pack/make.sh verify`. With that pack, blank-page auto-rotation and image hOCR passed. PDF text extraction initially revealed doubled spaces because geometric gaps and explicit separators were both interpreted as spaces; the glyph separator now spans the recognized gap. The PDF plus TXT test then passed with single spaces and exact original image-stream bytes. The `redo` test initially assumed a phrase occurred once although the truth contains it twice; it now compares occurrence counts before and after `redo`, and passed. This is evidence for Linux `pdftotext`, not macOS Preview.

The first 50-page attempt failed after its first page because the Linux private temporary mount used one fixed directory per job. The launcher now creates a separate private mount tree for each invocation, cleaned with the workspace. A real two-page regression test passed; the existing PDFium sandbox tests (3) and host sandbox tests (10) also passed. The successful 50-page rerun above exercised repeated invocations end to end.

A full repeat against `/tmp/ariad-p07-pack` and `/tmp/ariad-p07-pdfium` passed all seven `ocr_pipeline` tests in 132.60 seconds: blank-page orientation, cleaning an image-only page, text modes, image hOCR, repeated multi-page sandbox invocations, the warning for a synthetic PDF signature dictionary, and searchable PDF plus TXT with preserved source image streams. Command: `ARIAD_TEST_TESSERACT_PACK=/tmp/ariad-p07-pack ARIAD_TEST_PDFIUM_PACK=/tmp/ariad-p07-pdfium cargo test -p ariad-host --features test-probe --test ocr_pipeline -- --test-threads=1`, run through the shared build lock.

## Accuracy comparison

The three authored fixtures with truth in `fixtures/manifest.toml` were processed through real `image.ocr` with the unsigned source-built Tesseract 5.5.4 pack and through `ariad-engine/1` using the `ariad-docling` 0.2.0 development runtime, `docling-slim` 2.142.0, system Tesseract 5.5.3, cached Docling models and the same pinned tessdata. This runtime was captured before the source PyTorch replacement; the Docling pack build did not complete and is not claimed as a verified release pack. Both routes used only `vie` for the two Vietnamese samples and only `eng` for the English sample. The models match by SHA-256: `vie` `b6b49293d95d0b6dbd8780174627e82c75be957b6f4ed9862155540d6b00bb45`; `eng` `8280aed0782fe27257a68ea10fe7ef324ca0f8d85bd2fd145d1c2b560bcb66ba`.

All three samples produced CER 0.0 and WER 0.0 on both routes, so each measured CER gap was 0.0 percentage points. The small corpus consists of `vi-garden-300dpi.png`, `vi-river-200dpi.png` and `en-map-room-150dpi.png`; it does not establish accuracy on complex or degraded scans. `bench/results/ocr-eval.json` records the truth and input hashes, exact output text and hashes, versions and scores. The scorer normalizes to NFC and collapses whitespace while preserving case. The `docling_ocr_baseline.py` helper submits an actual conversion with `ocr=tesseract`, `lang`, `artifacts_path` and `tessdata_path`, then exports the Docling document text; `ocr_eval.py` uses `jiwer` for the per-sample scores.
