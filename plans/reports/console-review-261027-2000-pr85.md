## 1. Verdict

Needs minor fixes. The change fixes the root cause rather than masking it: it makes the tests wait for the engine-ready state the app exposes, and the failing file-read assertion keeps its 5 s default. Before merging, cover the one cold-boot file pick that is still unprotected in `converter.spec.ts` and get CI green on the head commit. Nobody has run the `converter.spec.ts` changes yet.

### Root-cause assessment

The flake came from the first file pick on a fresh page. That pick awaited the worker's cold boot inside the 5 s `input-name` assertion. The boot downloads and compiles the 6.6 MB `ariad_wasm_bg.wasm`, opens OPFS and warms cached engines, and under 4 parallel WebKit workers it took longer than 5 s. I confirmed every link in that chain in the code:

- `handleFiles` awaits `start()` (the `init` request) before it sends `ingest` (`apps/web/src/components/converter/converter-app.tsx:184-186`).
- `init` resolves only after the worker `context` resolves. That context runs wasm `init()`, `OpfsStore.open` and `warmCachedEngines()` (`apps/web/src/converter/worker.ts:12-28`, `apps/web/src/converter/session.ts:179`).
- The storage badge (`Private browser storage` / `In memory`) renders only after `setEngine(info)` runs in `start().then` (`converter-app.tsx:113-126`, `348-353`). The badge is therefore a deterministic engine-ready signal and not a heuristic. The regex `/browser storage|In memory/` cannot match the static indicator text that is present before boot.
- Once the badge shows, `ingest` goes to a booted worker. That worker runs `store.putInput` plus a native `core.inspect`; Pandoc loads only on `convert` (`session.ts:59-89`, `browser-engines.ts:35-50`). So the 5 s `input-name` budget now covers only the file read, as intended.
- `reset()` in the spec now waits for `Files were removed from this device.`. The app sets that status only after the worker answers `reset` (`converter-app.tsx:283-300`). When the worker is recycled, the client spawns a fresh worker and sends `init → retire → reset` in that order (`client.ts:37-58`, unit-tested in `apps/web/test/client.test.ts:74-76`). The worker queue serializes them (`worker.ts:30-35`, `session.ts:217-225`). The status therefore means the replacement worker has booted.
- I found no app race hidden by the new reset wait. A file picked while `reset` is still in flight is queued behind `reset` in the worker, so `reset` can never delete the new input. The old test passed only because the next pick's 5 s budget absorbed the replacement worker's boot.
- `page.getByRole("status")` is unique. The only `role="status"` element in `apps/web/src` and `packages/ui/src` is `converter-app.tsx:335`.
- Progress events come only from `engineResponse` during `convert` (`wasm-cache.ts:87-131`). No progress event can overwrite the reset status after it is set.

The 60 s `ENGINE_BOOT` value is a bound on a separate, explicit phase. It is not a longer timeout on the assertion that failed. A boot that never finishes still fails the test, now at an assertion that names the real cause. The worker's evidence also supports the fix: 8 of 25 baseline runs failed and 26 of 26 fixed runs passed. If the 32 % failure rate had persisted, 26 straight passes would have about a 0.68^26 ≈ 5e-5 chance. I could not re-check the traces (they are on the ASUS box) and took them from `plans/reports/worker-web-flake-opus55.md`.

## 4. Test gaps that matter

- **Unverified commits.** `0e6cd8d` and `22af4cc` (`converter.spec.ts`) have no recorded run. The Argon report says "No build or test was run", and `22af4cc` has no report at all. The 240-run of `heavy-routes.spec.ts` stopped at 26, and it ran against the build in `~/Codes/01-AriadShift-wt-web-heavy`, not against this branch. Before merging, run once on the PR head: `pnpm exec playwright test --project=webkit e2e/converter.spec.ts e2e/heavy-routes.spec.ts --repeat-each=20 --retries=0` with 4 workers, plus a green CI `web` job. Note that CI runs with `retries: 1` (`playwright.config.ts:10`), so CI alone is a weak flake signal.
- **The "pick while the engine boots" path loses coverage.** Waiting for the badge everywhere means the e2e suite now barely tests a user who picks a file before the boot finishes, even though `handleFiles` joins the in-flight `init` promise in that case. Only the oversized-IR test (finding 1) and the Chromium-only `offline.spec.ts` "works offline" test still take that path. `apps/web/test/converter-app.test.tsx` uses a fake client that answers `init` at once. If finding 1 is fixed with option (a), WebKit and Firefox lose this path entirely. Keep one test for it deliberately, using option (b) or a unit test whose fake client defers `init`.
- **Boot latency has no budget anywhere.** With a 60 s ceiling, a regression that makes the boot 10 times slower would pass every test. The old tests never measured boot on purpose either, so this is not a regression. It deserves a note if boot time matters for the product.
