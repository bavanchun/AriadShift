# Verification: high and medium findings on `origin/fix/v1-security-audit`

Reviewed 2026-10-27 (Asia/Saigon). The review was read-only and used local remote-tracking refs; no fetch, build or test was run. Refs: security `de92a19`, `origin/dev` `e6bd29b`, `origin/feat/v1-hardening` `dcb34bc`, `origin/feat/cloud-product` `796c83e`. These match the earlier reports.

Sources verified:

- `plans/reports/console-review-261027-2000-security-audit-branch-server.md`: findings F1 to F5.
- `plans/reports/console-review-261027-2000-security-audit-branch-web.md`: findings 1 and 2.

Server F1 and web finding 1 describe the same defect.

## 1. Verdict

**Needs fixes.** The CSP storage-origin defect (F1) is confirmed and blocks the merge. Its consequence: on any compose deployment whose S3 endpoint is not `http://localhost:8333`, browser uploads and downloads are refused. The other medium findings are confirmed. The exception is F5, which is only partly confirmed: its defect is real, but the failure scenario in the earlier report is wrong as written. A corrected scenario works from a single client, and the same mechanism scales to the global budget (new finding N1).

### What I tried in order to disprove each finding

- **F1.**
  - I searched the whole branch for `ARIADSHIFT_WEB_STORAGE_ORIGINS`. It appears only in `route-headers.mjs`, `headers.test.ts`, `docs/web.md:91` and the Dockerfile; no compose file, env example or workflow sets it.
  - Presigned URL origin: the S3 store uses `object_store`'s default path-style requests (`storage.rs:727-739` sets no virtual-hosted option), so the origin is exactly `ARIAD_S3_PUBLIC_ENDPOINT`.
  - Regression check: cloud-product's nginx config has no CSP, so uploads work there today.
  - Scope: `file://` deployments are unaffected, because their presigned URLs are on the API origin, which is already in `connect-src`.
- **F2.** The Dockerfile diff from `a882c23` touches no build step. `dev` and hardening also lack the Typst build while depending on `@ariadshift/ariad-typst`, so the defect is inherited.
- **F3.** All four refs were checked with `git grep`. The workspace members and the absence of a `[tool.uv] conflicts` entry were confirmed.
- **F4.** I compared the response keys of `/v1/blobs/{token}` with `jq` across all four refs. Only hardening lacks 408 and 429.
- **F5.** I traced the anonymous upload admission and found the pending cap, which refutes the stated scenario. I then traced the GET path for an alternative route: no per-key exclusivity, no rate limiter on blob routes, and reusable tokens with re-presigning. Trusted-header spoofing is not possible by default (`auth/mod.rs:186-209`).
- **web 2.** I checked `playwright.config.ts` for `bypassCSP`; it is not set. `next start` serves the build-time header table.

## 3. Contract and architecture (AGENTS.md / ARCHITECTURE.md)

- I found no violation. No new crate, service or runtime dependency was added, conversion logic is untouched, and the lockfiles are committed with exact pins.
- **Undocumented contract.** `ARIADSHIFT_WEB_STORAGE_ORIGINS` is a new public build-time variable. It is documented only in prose at `docs/web.md:91`. The branch-wide grep confirms it is absent from `self-hosting.md`, from every env example and from the compose file.

## 4. Test gaps that matter

- No test ties the compose web build args to the server's public URLs. `build-wiring.test.ts` checks only `NEXT_PUBLIC_*` names, and that is how F1 shipped.
- No browser run exercises the hashed static-export CSP (nginx or `_headers`). `next start` serves `'unsafe-inline'`. A run that fails on `securitypolicyviolation` would catch F1 and web 2.
- No test holds GET slots: there is no regression test showing that one principal cannot take its workspace's full share, or the global budget, through repeated GETs of one token (F5, N1).
- On hardening, `openapi_drift` fails (F4). Run it after any port.
- None of the security fixes has been compiled or tested on any target branch.
