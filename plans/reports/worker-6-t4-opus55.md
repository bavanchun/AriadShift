## Outcome

- `GET /v1/limits` returns the caller's plan, conversion limits, retention and quotas. It works with or without credentials, using the same `Caller` extractor (and rate limit) as every other `/v1` route. Each quota (`uploads_per_day`, `jobs_per_day`, `input_bytes_per_day`, `pending_uploads`, `concurrent_jobs`) is `{limit, used, remaining}`, with `null` limit and remaining when unlimited. The values come from the same counters the upload and job admission checks use, so `remaining` is exactly what the next check lets through. The response is `Cache-Control: private, no-store`.
- `DELETE /v1/uploads/{id}` deletes the stored object and retires the record. It returns `204`, also when the upload is already `deleted` or `expired`; `404` for an unknown or foreign upload; and `409 conflict` when any job uses the upload (delete the job instead).
- `/v1` is frozen. `info` carries `"x-stability": "stable"` and a sentence in its description. `tests/openapi_v1_snapshot.rs` compares the generated document with the frozen snapshot `crates/ariad-server/tests/snapshots/openapi_v1.json`: breaking changes fail and additive ones pass. `docs/api.md` has the versioning and deprecation policy.
- The SDK (`packages/sdk/src/client.ts`) wraps both operations as `deleteUpload(id)` and `limits()`.

## Design notes

- **Why the upload record is retired, not deleted.** `retire_upload` sets `status = 'deleted'` and erases `filename`, so no personal data remains. The row has to stay for three reasons. Upload admission counts deleted uploads over 24 hours, so dropping the row would let a caller create and delete uploads past the daily byte quota. The sweeper uses `deleted` rows to remove PUTs replayed after deletion while the presigned URL is still valid, and to remove the object once more at expiry. The existing 30-day metadata prune then removes the row.
- **Race with job creation.** `delete_upload` locks the upload row `FOR UPDATE`, checks that no job exists, and retires the upload. `create_job` now takes `FOR SHARE` on the same row inside its transaction and requires `completed`. Either the deletion sees the committed job and returns `409`, or job creation sees the committed deletion and returns `409`. Without the share lock, the foreign-key check's `KEY SHARE` lock does not conflict with the status `UPDATE`, so a job could have been queued with no input. The runtime role already has `UPDATE` on `uploads`, which row locks need.
- **Order of deletion.** The database commit happens first and the object is deleted after it. If the object delete fails, the client gets `500` and a retry deletes it again (the `deleted` branch always deletes the object). The sweeper is the backstop.
- **Quota semantics.** `uploads_per_day` uses the `jobs_per_day` cap, as upload admission does. `input_bytes_per_day.used` is the larger of the bytes uploaded and the bytes submitted to jobs, because both checks apply to a new file. `pending_uploads.limit` is `concurrent_jobs`, or 64 when that is unlimited.
- **Snapshot checker.** It follows the direction of each schema. Request schemas may not narrow: no fewer types, enum values or nullability, no new or tightened bounds or formats, no newly required fields, no `additionalProperties: false`. Response schemas may not widen: no new types, no new nullability, no required property becoming optional, no looser bounds. Removed properties, paths, operations, `operationId`s, response codes, media types, response headers, parameters and component schemas fail in both directions, and so does a removed security alternative such as anonymous access. New enum values pass in both directions, matching the documented rule that clients tolerate unknown values. A changed `oneOf`/`anyOf`/`allOf` (other than nullable wrappers, which the current document is limited to) is reported for review. `$ref` pairs are compared once per direction, which also stops recursion.
- `info.version` still follows the crate version. The policy treats it as outside the contract.
