# Worker Report: Web Account and Auth Fixes (`fix/web-account-auth`)

## Summary

Resolved web account and authentication issues and round-2 security review items across `@ariadshift/web` and `@ariadshift/auth`:

1. **Surface `/api/auth/token` failures instead of falling back to anonymous `/v1` requests**: `auth.apiToken()` throws a typed `AuthError` when `/api/auth/token` fails (distinguishing `401` `unauthorized` from `503` `unavailable`, `429` `rate_limited`, network failures `network_error`, and malformed token payloads `invalid_token_response`), and `createJobsApi` (`signedIn: true`) fails closed before dispatching any `/v1` request while preserving temporary retry wording for `503`, `429`, and network failures.
2. **Require a 15-minute fresh session on `/delete-user` for all accounts while keeping password verification for password-backed accounts**: Added a before-hook on `/delete-user` in `services/auth/src/auth.ts` that enforces a non-empty `password` whenever the user has a `credential` account with a password hash and enforces a 15-minute session freshness window (`DELETE_USER_FRESH_AGE_S = 15 * 60`, returning `reauth_required` when older) without changing Better Auth's global `session.freshAge` for passkey or unlink routes. Updated `AccountActionsSection` and `auth.hasPassword()` / `auth.deleteAccount(password?)` so social-only users confirm deletion from a fresh session and stale sessions prompt the user to sign in again.
3. **List and revoke OAuth consents and registered OAuth clients from the Account page**: Enriched `/oauth2/get-consents` with client metadata (`clientName`, `clientUri`), ensured `/oauth2/delete-consent` and `/oauth2/delete-client` revoke active `oauthAccessToken` and `oauthRefreshToken` rows while serializing on `OAUTH_TOKEN_LOCK_KEY` (`SERIALIZED_OAUTH_PATHS`) with `/oauth2/token` and `/oauth2/revoke`, exposed `listOAuthConsents`, `deleteOAuthConsent`, `listOAuthClients`, and `deleteOAuthClient` on `AuthApi`, added `ConnectedAppsSection` to `AccountPage` with explicit disclosure of the 15-minute signed access token lifetime, and documented the behavior in `docs/web.md`.

## Root Cause & Changes by Issue

### 1. API Token Refresh Error Handling (`apps/web`)
- **Root cause**: `createBetterAuthApi().apiToken()` returned `undefined` whenever `/api/auth/token` responded with a non-OK HTTP status or a body without a string `token`, and `createJobsApi` treated an `undefined` bearer token from `auth.apiToken()` identically to an anonymous caller—sending `/v1/jobs` requests without an `Authorization` header and masking expired/revoked sessions as generic anonymous API responses.
- **Changes**:
  - [`apps/web/src/components/account/auth-api.ts`](apps/web/src/components/account/auth-api.ts): Updated `apiToken()` (and its doc comment) to clear `cachedToken` and throw `AuthError` with `code: "unauthorized"` on `401`, `code: "rate_limited"` on `429`, `code: "unavailable"` on `503`/5xx, `code: "network_error"` on network failure, and `AuthError(..., response.status, "invalid_token_response")` when a `200 OK` body does not contain a non-empty string `token`.
  - [`apps/web/src/components/account/jobs-api.ts`](apps/web/src/components/account/jobs-api.ts): Added `requireBearerToken(auth)` used when `signedIn` is `true` so any error or empty token from `auth.apiToken()` fails closed before issuing an unauthenticated `/v1` network call, mapping `401` to `unauthorized` (`"Your session has ended. Sign in again."`) and `503`, `429`, and network errors to temporary retry messages.
  - Tests in [`apps/web/test/account-auth-api.test.ts`](apps/web/test/account-auth-api.test.ts), [`apps/web/test/account-jobs-api.test.ts`](apps/web/test/account-jobs-api.test.ts), and [`apps/web/test/account-jobs.test.tsx`](apps/web/test/account-jobs.test.tsx).

### 2. Social-Only Account Deletion and 15-Minute Session Freshness (`services/auth`, `apps/web`)
- **Root cause**: `AccountActionsSection` required a non-empty password in the `"Delete your account?"` dialog and always sent `{ password }` to `client.deleteUser({ password })`. Better Auth's `/delete-user` endpoint permits passwordless deletion when the session is within `session.freshAge` (24 hours by default), which would allow password-backed accounts to bypass the password check if callers omitted `password` and allowed a 24-hour window instead of 15 minutes, whereas social-only users have no `credential` password and were blocked by the UI form.
- **Changes**:
  - [`services/auth/src/auth.ts`](services/auth/src/auth.ts): Added a `hooks.before` middleware on `/delete-user` that requires a non-empty `password` when a `credential` account with a password exists (`PASSWORD_REQUIRED`) and requires `session.session.createdAt` to be at most `DELETE_USER_FRESH_AGE_S` (15 minutes) old for all accounts, throwing `APIError("BAD_REQUEST", { code: "reauth_required", message: "Sign in again before deleting your account." })` when older while leaving Better Auth's global `session.freshAge` unchanged for passkey and unlink routes.
  - [`apps/web/src/components/account/auth-api.ts`](apps/web/src/components/account/auth-api.ts): Added `hasPassword()` (inspecting `client.listAccounts()` for `providerId === "credential"`), made `password` optional in `deleteAccount(password?: string)`, and mapped `reauth_required` / `SESSION_EXPIRED` responses to a typed `reauth_required` `AuthError`.
  - [`apps/web/src/components/account/account-actions-section.tsx`](apps/web/src/components/account/account-actions-section.tsx): Queries `auth.hasPassword()` on mount; when `false`, renders a fresh-session confirmation dialog without a password input and invokes `auth.deleteAccount(undefined)`. When deletion is refused with `reauth_required`, displays the re-authentication message and a `"Sign in again"` link to `/sign-in?next=%2Faccount`.
  - Tests in [`services/auth/test/auth.test.ts`](services/auth/test/auth.test.ts) (both memory adapter and PostgreSQL), [`apps/web/test/account-auth-api.test.ts`](apps/web/test/account-auth-api.test.ts), and [`apps/web/test/account-pages.test.tsx`](apps/web/test/account-pages.test.tsx).

### 3. OAuth Consents and Registered Clients Management & Revocation Serialization (`services/auth`, `apps/web`, `docs`)
- **Root cause**: `@better-auth/oauth-provider` exposes `/oauth2/get-consents`, `/oauth2/delete-consent`, `/oauth2/get-clients`, and `/oauth2/delete-client`, but `AccountPage` had no UI or `AuthApi` methods for listing or revoking authorized OAuth apps and dynamically registered clients. Furthermore, `@better-auth/oauth-provider`'s `deleteConsentEndpoint` and `deleteClientEndpoint` only deleted the `oauthConsent` or `oauthClient` row without revoking issued `oauthAccessToken` and `oauthRefreshToken` rows or serializing against concurrent `/oauth2/token` refreshes, and `getConsentsEndpoint` returned raw `clientId` values without `clientName`.
- **Changes**:
  - [`services/auth/src/auth.ts`](services/auth/src/auth.ts):
    - In `hooks.before` for `/oauth2/delete-consent`, verifies ownership of the consent and deletes all `oauthAccessToken` and `oauthRefreshToken` rows for `(clientId, userId)` so refresh tokens fail immediately after revocation.
    - In `hooks.before` for `/oauth2/delete-client`, verifies ownership of the `oauthClient` row and deletes all `oauthAccessToken`, `oauthRefreshToken`, `oauthConsent`, and `oauthClientResource` rows for `clientId`.
    - In `hooks.after` for `/oauth2/get-consents`, enriches each consent item with `clientName` and `clientUri` from `oauthClient`.
  - [`services/auth/src/oauth-lock.ts`](services/auth/src/oauth-lock.ts): Added `/api/auth/oauth2/delete-consent` and `/api/auth/oauth2/delete-client` to `SERIALIZED_OAUTH_PATHS` so consent and client revocation serialize on `OAUTH_TOKEN_LOCK_KEY` with `/api/auth/oauth2/token` and `/api/auth/oauth2/revoke`.
  - [`apps/web/src/components/account/auth-api.ts`](apps/web/src/components/account/auth-api.ts): Added `OAuthConsentInfo`, `OAuthClientInfo`, `listOAuthConsents()`, `deleteOAuthConsent(id)`, `listOAuthClients()`, and `deleteOAuthClient(clientId)`.
  - [`apps/web/src/components/account/connected-apps-section.tsx`](apps/web/src/components/account/connected-apps-section.tsx) & [`apps/web/src/components/account/account-page.tsx`](apps/web/src/components/account/account-page.tsx): Added the `"Connected apps"` section displaying authorized apps (with scopes and timestamp) and user-owned registered OAuth clients, with confirmation dialogs stating that revoking stops new tokens and token refresh at once while signed access tokens already issued (15-minute lifetime) keep working until they expire.
  - [`docs/web.md`](docs/web.md): Documented OAuth consent and client revocation (immediate refresh revocation, 15-minute signed access token lifetime, pre-issued authorization code behavior) and 15-minute fresh-session account deletion.
  - Tests in [`services/auth/test/auth.test.ts`](services/auth/test/auth.test.ts) (both memory adapter and PostgreSQL), [`services/auth/test/oauth-path-safety.test.ts`](services/auth/test/oauth-path-safety.test.ts), [`services/auth/test/oauth-postgres.test.ts`](services/auth/test/oauth-postgres.test.ts), [`apps/web/test/account-auth-api.test.ts`](apps/web/test/account-auth-api.test.ts), and [`apps/web/test/account-pages.test.tsx`](apps/web/test/account-pages.test.tsx).

## Assumptions Recorded

1. Top-level `options.hooks` (`before` and `after` middlewares via `createAuthMiddleware`) in `buildAuthOptions` are used rather than adding extra entries to `options.plugins`, preserving the exact 5-plugin invariant tested in `services/auth/test/auth.test.ts`.
2. When `hasPassword()` fails or has not resolved yet, `AccountActionsSection` defaults to `hasPassword = true` (requiring a password) so password-backed accounts always default to the stricter prompt.
