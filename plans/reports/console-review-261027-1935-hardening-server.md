# Review: `feat/v1-hardening` vs `dev`, scope `crates/ariad-server` and `schemas/`

Date: 2026-10-27. Reviewer: console reviewer (read-only). Range: `git diff origin/dev...origin/feat/v1-hardening -- crates/ariad-server schemas/` (31 files, +8137/-171). I read the full diff plus the code it touches: `auth/mod.rs`, `create_job`, `purge_job`, the sweeper's upload queries, the migrations' plan seeds and indexes, `docs/api.md` §stability, `docs/server.md` §storage, `justfile` and `scripts/ci-scope.sh`.

## 1. Verdict

**Needs fixes (minor).** I found no critical or high defects. Auth, tenant isolation, job listing and the delete/create race are correct. One medium gap in the freeze mechanism should be closed before merge, because it undermines the stated goal of freezing `/v1`. The other findings can land as follow-ups.

Verified non-issues, so they are not re-raised:

- **`DELETE /v1/uploads/{id}` vs `POST /v1/jobs` race.** The `FOR UPDATE` in `delete_upload` and the `FOR SHARE` added in `create_job` (`api/jobs.rs:179-188`) order correctly under READ COMMITTED. Whichever commits second sees the other's committed state. There is no deadlock, because the delete path takes no subject lock.
- **Job list isolation and paging.** Filtering by `workspace_id`, rejecting anonymous callers, using a microsecond keyset cursor with an `id` tiebreak, and bounding the cursor length are all correct. `jobs_workspace_created_idx` exists. The integration tests cover tenants, API-key and JWT parity, deleted inputs and stability across inserts.
- **JWKS cache.** `find()` rechecks the cache after every refresh. A failed or throttled refresh cannot extend trust beyond 15 min or bring back a rotated-out key. Algorithm, issuer, audience and expiry checks are unchanged.
- **MCP audience separation.** REST JWTs (`aud` = auth origin) are refused on `/mcp`, MCP tokens are refused on REST, and anonymous callers are refused. Credentials are stripped before the handlers run.
- **`/v1/limits` arithmetic.** It matches `admit_upload` (uploads use the `jobs_per_day` cap) and `Entitlement::admit`. `remaining` uses the larger of the two byte meters, which is the right conservative bound.
- **OpenAPI diff vs `dev`.** All changes are additive (new paths, response headers, `x-stability`, descriptions). Nothing existing was removed or narrowed. The snapshot currently matches `schemas/openapi.v1.json` byte for byte.
- **Removed `ariad-server openapi` subcommand.** Nothing outside the crate referenced it; `just openapi` now runs the new `openapi` bin.

## 3. Contract or architecture violations

- I found none against AGENTS.md or ARCHITECTURE.md. `rmcp` is pinned in the workspace and the Decision Log records remote MCP authorization. No conversion logic was added to the server surface: MCP calls the existing handlers in-process.
- Contract inconsistency (finding 7): the frozen snapshot includes `/v1/blobs/{token}`, but `docs/api.md` says presigned URL forms may change.
- Contract precision (finding 6): nullable fields are not `required`, so the freeze does not cover their presence.

## 4. Test gaps that matter

- No test fails when an additive change is merged without refreshing the snapshot (finding 1).
- No test covers fairness of blob admission, such as one client holding all slots (finding 2), or a slow download that outlives the URL's remaining lifetime (finding 3). The current tests assert the cut-off as intended behaviour.
- No S3-backed test of `put_stream` with more than one part (finding 5). SeaweedFS would not catch the 5 MiB minimum anyway, so a unit-level guard or a local-only `debug_assert` is the practical option.
- No MCP test for a storage failure in `inline_upload` (status code and the stranded pending upload, finding 4).
- No concurrency test for the delete/create race. The locking is correct by reading, but it is unproven by a test.

## 5. Unresolved questions

1. **Shared inputs (pre-existing, outside this diff, but it touches the new delete semantics).** `purge_job(OnRequest)` (`api/jobs.rs:~334`) deletes and retires the input upload even when a sibling job created from the same upload is still queued or running. MCP `convert` explicitly allows repeats. The new `FOR SHARE` guard protects only against `DELETE /v1/uploads`, not against `DELETE /v1/jobs/{sibling}` or the sweeper. Is a single job per upload the intended model? If so, `create_job` should refuse a second job; if not, purge should keep inputs that other jobs still reference.
2. **OAuth access tokens on REST (unverified; depends on `services/auth`).** The REST verifier accepts any JWT from the issuer whose `aud` equals the auth origin. It does not check `typ: at+jwt`, `client_id` or `azp`. If the OAuth provider can ever mint an access token with `aud` equal to the issuer origin (for example when no `resource` is given), a dynamically registered third-party client would get full REST access. Has the auth-service review confirmed that the provider issues JWTs only for `<ARIAD_PUBLIC_URL>/mcp`? Rejecting tokens that carry `client_id` on the REST verifier would be a cheap safeguard.
3. **`/mcp` Host check.** The Host check requires an exact match with `ARIAD_PUBLIC_URL`'s host:port. Do any supported deployments put the API behind a proxy that rewrites Host, or behind a path prefix (`resource_url` always uses `/mcp` at the root)? Either would turn every MCP request into a `403`.
4. **Production use of `file://`.** Is `file://` intended for production self-hosting? That decides whether findings 2 and 3 are medium or acceptable dev-only trade-offs.
