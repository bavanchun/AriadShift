# PR #84 review: server scope (crates/, schemas/, services/, migrations)

Branch `origin/feat/cloud-product` at `796c83e`, compared with merge base `8782c49` (`origin/dev` is at `e6bd29b`). The local refs could not be refreshed: `git fetch` and `gh` both needed approval. Reviewed read-only on 2026-10-27.

## 1. Verdict

**Needs fixes.** The one server change is correct for what it sets out to do: account deletion revokes the user's API keys first and stops if that fails. But self-service deletion now runs against an API that never learns a user is gone. There are also two medium integration defects to fix or decide on before merge: anonymous users get locked out after a canceled upload, and the server does not enforce the password confirmation the code comment describes.

### What is actually in scope

There are 91 commits, but only three files changed in this scope against the merge base: `services/auth/src/auth.ts` (+12 lines, Better Auth `user.deleteUser` with a `beforeDelete` that revokes API keys), `services/auth/test/auth.test.ts` (+41) and `infra/compose/docker-compose.yml` (+2 build args). Nothing changed under `crates/`, `schemas/` or `crates/ariad-server/migrations/`. The integration merge `c234afe` resolved its `crates/ariad-server` conflicts (for example `api/blobs.rs`) to dev's side. `git show --remerge-diff c234afe` shows no hidden edits under `crates/`, `schemas/`, `services/` or `infra/`; it does show one under `ARCHITECTURE.md` (finding L5).

Because the server code itself barely changed, most of this review looks at how the PR's new account, jobs and cloud flows use the existing jobs, quota, tenancy and auth code on `dev`.

## 3. Contract and architecture issues (AGENTS.md / ARCHITECTURE.md)

- **Design authority regressed by a merge commit (L5).** AGENTS.md makes ARCHITECTURE.md the design authority. The regression contradicts its own Decision Log, and it came in through an unreviewable change inside a merge commit.
- **Client relies on endpoints that are not in the contract.** The web calls `GET /v1/jobs` and expects `{jobs, next_cursor}` with `filename`. It also calls `DELETE /v1/uploads/{id}` and `GET /v1/limits`. None of these is in `schemas/openapi.v1.json`, in ARCHITECTURE.md §9.1, or in any server in the repository. `docs/api.md` calls them "deployment capabilities", yet the same page says the OpenAPI document wins whenever the two disagree. If `ariad-server` later adds any of them, the response shapes the web already assumes become an unwritten contract. Two of them (M1, M2) are what the server is actually missing. Either implement them in `ariad-server` (the owner) or drop the probing.
- **Account lifecycle decision is not recorded.** ARCHITECTURE.md:644 says "Every account owns a workspace (tenant) from day one". Self-service deletion changes the tenant lifecycle and data retention, but the PR adds no Decision Log entry. AGENTS.md asks for one when a change alters architecture.
- No violation of the conversion boundary: there is no conversion code in surfaces, and Pandoc and Docling stay out of process. No new crate. In this scope the only new dependency (`@noble/hashes`, MIT) is in `packages/sdk`, which is outside it.

## 4. Test gaps that matter

- **Deletion with plugin rows.** The e2e deletes a user with no passkey and no 2FA. Nothing proves that `passkey` and `twoFactor` rows cascade (or block) when Better Auth deletes the user. A failure here would also cause L1(b).
- **Password policy.** No test shows that `delete-user` without a password, or with a wrong one, is refused (M3).
- **Server state after deletion.** No test covers the deleted user's workspace: live jobs and uploads, a JWT used after deletion, or the workspace row (M1).
- **Anonymous cancel flow.** No test of an anonymous cancel followed by a new upload against the real server (M2). `run.sh` covers the daily upload cap only.
- **Auth CORS from a browser.** The account pages are tested only against mocked routes (`apps/web/e2e/account.spec.ts`). No browser test calls the real auth service, so CORS (`allowMethods` GET/POST, `allowHeaders` Content-Type/Authorization) is never checked for the passkey, 2FA, API-key and delete calls.
- **Mock-only unit test.** The `beforeDelete` unit test uses a mocked pool. The only real-database proof is the compose e2e, and I could not see whether it ran green on this PR (see questions).

## 5. Unresolved questions

1. Did the `Cloud E2E` workflow run and pass on PR #84's head `796c83e`? It runs only on path changes or the `cloud-e2e` label, and checking it needed `gh`, which was not approved.
2. Who is meant to serve `GET /v1/jobs`, `DELETE /v1/uploads/{id}` and `GET /v1/limits`: a later `ariad-server` change, or a hosted deployment outside this repository?
3. For a deleted account, is server-side data meant to stay until retention runs out (current behaviour, stated in the UI copy), or to be purged at once? This is a product and compliance call (M1).
4. Should account deletion require the password on the server for every user? That would mean passkey-only and social-only accounts need another confirmation route (M3).
5. Does Better Auth 1.7.12's `delete-user` match the behaviour M3 assumes? It needs checking against the installed package.
