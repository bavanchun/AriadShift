# PR #84 review: web cloud mode, account pages, jobs page and SDK

- Branch: `origin/feat/cloud-product` (`796c83e`) against `origin/dev` (`e6bd29b`), merge base `8782c49`.
- Scope: everything under `apps/web` and `packages/` (73 files, about 11,400 added lines). The full diff for these paths was read, along with the code it touches: the SDK client and errors, the shared `Button`, the auth service's Better Auth and CORS configuration, and the server's event-stream lease cap.
- Method: read-only. Nothing was built, tested or executed. Line numbers refer to files on the branch.

## 1. Verdict

**Needs fixes.** Nothing blocks the architecture. Before merge, fix the open redirect after sign-in, the account pages dropping the API path prefix, and the auth-service failure modes in `/app`: an unreachable auth service takes anonymous cloud use down, and a failed sign-out leaves the session alive while the UI shows the user as signed out.

Checked with no issue found:
- No `dangerouslySetInnerHTML`, `innerHTML` or `eval` in the diff. Server strings, file names and emails render as React text.
- `totpUri` comes from the trusted auth service.
- Presigned PUT and GET requests never carry the JWT: Uppy's `signRequest` returns only the presigned URL and headers, and SDK downloads use plain `fetch`.
- The offline policy keeps `/api/auth/**`, `/v1/**` and presigned URLs out of Cache Storage, and activation purges old entries.
- The CSRF posture relies on Better Auth's Origin check plus `SameSite=Lax` host-only cookies. Auth POSTs send `content-type: application/json`, so they are preflighted. CORS exposes `set-auth-jwt` (`services/auth/src/app.ts:60-68`).
- SDK `sha256Hex` keeps its public export from the package index and accepts a superset of the old input types.

## 3. Contract and architecture notes

- **No conversion logic in a surface:** respected. The web only orchestrates `/v1` calls through `@ariadshift/sdk`.
- **SDK scope (ARCHITECTURE §9.1, "the SDK adds only upload, job-event and download helpers"):** the new `hash.ts` is part of the upload helper, so it is acceptable. The new runtime dependency `@noble/hashes` 2.4.0 (MIT) is not listed in §2.2. Consider adding it, as Uppy is.
- **ARCHITECTURE §8.3 and §10 edits in this PR:** the sequence participant was renamed from "Browser" to "Next.js (Better Auth)", and the Web row now says "Next.js (Better Auth) browser client". The web is a static export with no Next.js server, and `/app` does not use the Better Auth client: it uses the hand-written `CloudAuth` (`lib/cloud/auth.ts`). Only the account pages use `better-auth/client`. The new wording is inaccurate. Use "Browser (static web app)" and say which client each page uses, or unify the clients (finding 10).
- **§2.2 Uppy row** still says "Resumable multipart uploads", while the Decision Log and the code use one presigned PUT with `shouldUseMultipart: false`. The row predates this PR but is now visibly contradicted by it.
- **Turnstile under COEP on `/app`:** `docs/web.md:123-125` already records that the cross-origin Turnstile iframe has not been checked in a real browser under `Cross-Origin-Embedder-Policy: credentialless`. If Chromium or Firefox block it, anonymous cloud uploads cannot start on any deployment that sets a Turnstile key. This should be verified before the hosted tier, not after.
- **ARCHITECTURE §10 lists GitHub and Google sign-in for Web,** but neither `/sign-in` nor the `/app` dialog offers social sign-in. Accounts created through social sign-in elsewhere could not use the password-gated account actions (change password, 2FA, delete account). The gap needs to be either documented or scheduled.

## 5. Unresolved questions

1. Does `@base-ui/react`'s `Button` render `type="button"` by default? Several Cancel buttons sit inside `<form>`s without an explicit `type`: `account-actions-section.tsx:108`, `two-factor-section.tsx:186,236`, `api-keys-panel.tsx:262`, `passkeys-section.tsx:151`. If Base UI does not default to `button`, pressing Cancel in the delete-account dialog after typing the password would submit the form and delete the account. node_modules is not installed and the docs lookup was not permitted, so this could not be confirmed. Adding `type="button"` costs nothing either way.
2. Is persisting anonymous job ids in `localStorage` across visitors acceptable for the hosted tier (finding 12), given the "private by default" principle?
3. Should a transient auth-service failure for a signed-in user ever fall back to anonymous cloud use (finding 3b), or should it fail closed?
4. Is social sign-in (GitHub, Google) in scope for the web in this release, or should ARCHITECTURE §10 say it is API and desktop only for now?
