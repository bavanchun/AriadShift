## Verified findings

### Resolved medium: restore unconditional plain-file acceptance

The fresh lead review in `/home/vchun/Codes/ariadshift-ops/reports/r-3b-fuzz-packs-sol.md` was correct. In the earlier source at `pack_archive.rs:139–154`, File statistics were checked only after successful scanning, and scan/writer agreement only after successful extraction. If the shared File path rejected an input in both scanner and writer, both assertions were skipped and the harness returned successfully. This weakened the original unconditional `.expect("a plain file always scans")` property. It was a real oracle coverage defect, without implying a current production extraction defect.

My prior review missed assertion reachability: I checked the retained statistics assertions and success-path scanner/writer agreement without comparing their execution conditions against the original unconditional File acceptance requirement. A positive plain-file test and passing fuzz runs did not validate the missing rejection path. The earlier no-findings verdict was wrong for this invariant and is superseded by this correction.

Final commit `16b9423` restores unconditional `scan.expect`, entry count 1, exact input byte count, bounded extraction `result.expect`, and exact scanner/writer statistics agreement for File. Every admitted input is at most 16 KiB and one entry, within the 1 MiB/1024-entry budgets and a fresh writable root, so success is the correct invariant. Archive formats retain typed rejection. Existing partial-output confinement checks still execute before these assertions. The completed mutation-control and real-production evidence below verifies the repair. No remaining actionable finding was identified in the final narrow delta.
